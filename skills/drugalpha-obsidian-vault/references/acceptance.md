# 检索验收

用实际研究问题检查知识库的可用性和证据覆盖。试导入至少验一组。交付时优先做一次新会话验收。用户明确要开新对话且客户端可代开时，提交独立的只读任务并查看结果。有些客户端需要用户手动开会话，可直接给出能复制的验收问题。

## 单家公司建库完成条件

1. **公司双链**　核对实质讨论该公司的归档资料，补齐指向该公司资料入口的原生双链。抽查能从入口找到重点披露并打开原件，也能从来源笔记回到入口。
2. **药物双链**　按约定范围完成药物清单，用标准名和已核实别名扫描来源并核对上下文。库内原件支持的药物建立或复用单药笔记，关联实质来源并补上可核实的原件页码或稳定定位。证据不足的条目留在清单并标明缺口。已具备原件证据、但尚未补链的条目应在本批完成。
3. **公司笔记**　检查 `key-driver.md` 有短期和长期逻辑、核心变量、验证条件及证据，`notes.md` 覆盖库内已核实的实质变化，能区分实际进展与当时预期，并追溯原件。逐项记录证据缺口和待用户确认的判断，仍是占位或资料未梳理的笔记标为待补齐。
4. **逐家验收**　检查链接目标、标题锚点和原件定位，用实际投研问题抽查别名或标准名到单药笔记、来源和原件的路径，并区分已发生进展、当时预期和待核实事项。公司双链、药物双链和公司笔记均通过后，才标记该公司建库完成。已有判断的待审改稿在交付中注明状态。本批公司全部通过后再进入下一批。已记录的证据缺口可随验收结果交付。

## 样例和最终验收

1. 先核对目录、Frontmatter、同名项、双链目标和标题锚点。按公司、资料类型、日期或报告期筛出样例，区分原件、来源 Markdown 和研究笔记。批次完成后重新检查受影响的目标。已建立公司资料入口时，抽查公司来源链接能否跳到入口并沿入口返回来源。待入库批次逐家验收两份笔记，核对新公司已建立 `notes.md` 和注明证据缺口的 `key-driver.md`，已有公司已将实质变化及出处写入 `notes.md`，并同批提供 `key-driver.md` 具体拟改文或注明无实质变化。将两份笔记与归档清单一并交用户确认，核对批准后的写回与链接。
2. 每家公司各选一道真实投研问题。给新会话 Vault 绝对路径、公司或药物别名、问题和截至时间。仅提供这些输入和验收要求，由它自己找笔记、证据和页码。用户要求只用本地资料时，只读 Vault，使用库内证据作答，外部搜索和 MCP 均排除。
3. 对每题检查是否能用标准名和已验证别名找到同一药物，能否从单药笔记到来源笔记、打开原件并读到实际支撑结论的物理 PDF 页。对 Word、Excel 等使用适合的原件定位。已归档资料缺少相关披露时，结论写「库内未核实」，并指出需要补哪类原件。
4. 要求分别回答「已发生」「当时预期／待核实」，逐项给资料标题、披露日期、原件和页码。区分同一药不同试验、治疗线别、地区及疾病。注意来源转述和表格简写可能有歧义。结论应以正文或相应的一手原件证据为准，并说明实际核实到的范围。
5. 验收分三项报告。**检索链路**记录别名、链接、页码是否走通。**证据覆盖**记录实际进展、后续兑现情况和仍缺的材料。**笔记覆盖**记录已在原件找到、但尚未从现有笔记直接链接到的证据。明确抽样范围和实际使用的客户端或文件检索方式。只读验收先报告待修项，得到修改指令后再补写。

## 可改写的试跑题型

- **同一药物，不同地区及适应症**　分别问三项研发进展和曾经预计的顶线。核对首例给药、完成入组和实际读出三个节点，分别引用本地公司原件与合作方材料。
- **同一药物，多项注册研究**　让 AI 先用别名定位，逐项对照中报的期中分析计划和后续三季报。特别检查它能否把早期队列数据、另一款药物的期中分析和本药 III 期读出分别识别。
- **注册进展与商务合作**　要求按治疗线别解释关键试验、监管认定和附条件上市申请门槛。再核对合作签署、首付款实际到账、选择权行使及后续里程碑付款。试验获准、认定、申报和获批各用对应证据。
